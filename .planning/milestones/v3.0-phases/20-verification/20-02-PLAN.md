<objective>
Build the permanent **Verification** review section (SHW-15 / D-04): all eight restyled components
in one flow, so the cross-component coherence pass D-01 asks for has a screen to happen on. Today
the eight demos are spread across `ButtonsSection` / `RangeSection` / `SelectionSection` /
`ListSection`, and the question "do all eight read as one material family, or as eight separate
approximations of it" cannot be answered by eye at all.

Then audit those four existing sections for state completeness and top up any state that is
missing. Existing sections are audited and topped up, never restructured (D-04).

Purpose: the human three-theme sign-off in 20-07 is a visual comparison across eight components and
three themes. Without one screen holding all eight side-by-side at equal visual weight, the
reviewer compares from memory across four scroll positions — which is how "each state is correct"
(what Phases 17-19 already answered) gets mistaken for "all eight read as one family" (what this
milestone still owes).

Output: one new showcase section file, one registry line in `ShowcaseApp.kt`, and state top-ups in
the four existing sections.
</objective>

Create `showcase/src/main/kotlin/com/mordred/showcase/sections/VerificationSection.kt`, package
`com.mordred.showcase.sections`, exposing `@Composable fun VerificationSection()`.

**Section header copy is exactly `"Verification"`** (UI-SPEC Copywriting Contract), rendered with
`AeroTheme.typography.title` and `colors.onBackground`, matching every existing top-level section
name's register.

**Eight demo blocks, in this fixed declared order** (the milestone's own listed order — this order
is load-bearing so sign-off captures are positionally comparable across the three themes):
`AeroButton`, `AeroOutlinedButton`, `AeroSwitch`, `AeroSegmentedControl`, `AeroSlider`,
`AeroRangeSlider`, `AeroProgressBar`, `AeroListItem`. Each block's caption is the component's bare
name, rendered with `AeroTheme.typography.label` (11sp/Bold) and `colors.labelText`, single-line, no
wrap.

**Inside each block, state tiles in the fixed order `default` → `hover` → `press` → `focus` →
`disabled`.** Each tile is a labeled column: a live component instance with a small text label
beneath it naming the state, so two states that render identically stay distinguishable to the
human signer. **No forced or static styling is used to fake a state** — 17-04's precedent: the live
theme switcher plus a real mouse and keyboard makes transient states genuinely reviewable without
bypassing the real state-resolution path. The `hover`, `press` and `focus` tiles therefore hold
ordinary enabled instances, and their labels name both the state and the gesture that reaches it
(`"hover — mouse over"`, `"press — click and hold"`, `"focus — Tab"`). The `default` tile holds a
plain enabled instance; the `disabled` tile passes `enabled = false`.

**A component renders only the tiles for the states it actually supports — never an empty
placeholder tile.** Concretely, from the shipped public signatures:
  - `AeroButton`, `AeroOutlinedButton`, `AeroSwitch`, `AeroSegmentedControl`, `AeroSlider`,
    `AeroListItem` — all five tiles (each takes `enabled: Boolean = true` and is keyboard-focusable).
  - `AeroRangeSlider` — four tiles: `default`, `hover`, `press`, `disabled`. The `focus` tile is
    omitted entirely because this component has no keyboard-focus tracking at all (its custom
    `Canvas` never acquires focus; explicitly accepted as deferred out of scope at 18-04). Record
    that omission in the file's KDoc so a future reader does not read it as an oversight.
  - `AeroProgressBar` — one tile, `default`. Its public signature carries no `enabled` parameter and
    the component has no hover/press/focus surface at all (18-03: "AeroProgressBar has no
    enabled/disabled state and none was added"). Use the determinate overload with a fixed progress
    value; do not invent states for it.

**Layout:** the section reuses `ShowcaseApp.kt`'s existing outer scroll container — do NOT introduce
a second, nested scroll region. Use `Arrangement.spacedBy(16.dp)` between demo blocks and
`Arrangement.spacedBy(8.dp)` between a block's caption and its tile row, per the UI-SPEC's spacing
scale. Each demo block sizes to `max(caption, control)`: give the block a `Column` whose width is
its intrinsic content width so the caption never truncates (this matters for `AeroSwitch`, whose
caption is wider than its 36.dp track). **Every block carries equal visual weight** — no larger
card, no highlighted border, no emphasis on any one of the eight, or the coherence judgment the
section exists for would be biased by the layout.

Drive each interactive component with its own local `remember { mutableStateOf(...) }` so the demos
are genuinely interactive, exactly as the existing sections do. Compose the shipped public
components directly — never fork or copy demo code from the existing sections.

Add a short section-level prose line under the title, in the register `ButtonsSection` already uses,
stating that hover / press / focus are transient and are reviewed live across all three themes via
the theme switcher above.

Then register the section in `showcase/src/main/kotlin/com/mordred/showcase/ShowcaseApp.kt`: add the
import and one call inside the existing outer `Column`, wrapped in the same
`Column(verticalArrangement = Arrangement.spacedBy(16.dp)) { Text(...); VerificationSection() }`
title-wrapper shape the "Foundation" and "Primitives" entries use. Place it as the FIRST content
section, immediately after `ThemeSwitcher` and before the "Foundation" block, so the coherence grid
is on screen without scrolling at sign-off time. Change nothing else in `ShowcaseApp.kt`.
