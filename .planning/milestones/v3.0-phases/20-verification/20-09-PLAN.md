<objective>
Make the on-fill label colour a property of the colour scheme rather than a per-call-site
computation, so that within one theme the label is ONE colour across every component and every
interaction state.

**Why.** 20-04 introduced `resolveLabelColor(fillTop, fillBottom, backdrop)` to fix a real defect:
the label set no `color` and inherited `LocalContentColor`, measuring 1.70:1 on AeroDark at rest.
The fix worked for the at-rest case. But the call sites pass `style.fillTop`/`style.fillBottom`, and
`resolveSegmentStyle` folds hover (`hoverLighten()`), press (`effectiveProgress = 1f`) and the
selection animation into that fill. So the label is recomputed from a fill that moves with
interaction, and flips black↔white whenever the moving fill crosses the contrast midpoint — text
that changes colour because the pointer passed over it.

The maintainer's rule, recorded at the 20-08 checkpoint on 2026-07-29:

> Per theme, ONE text colour. Not per element, not per state. Exceptions are allowed but must be
> rare and justified — where it would otherwise be illegible or awkward, or where making the text
> colour interactive is genuinely useful for that element.

Classic already behaves this way (white everywhere, unconditionally) and is the reference. AeroBlue
and AeroDark do not.

This also completes D-12 rather than contradicting it. D-12 asked for one source of truth and got
one shared *function*; the rule above tightens it to one resolved *value* per theme.

**The trap to avoid.** The old algorithm quietly rescued individual fills by picking a different
colour for each. Removing it removes that rescue, so contrast must be measured FRESH against every
fill the single colour now lands on. Carrying over 20-04's table would certify numbers that no
longer describe the code — the exact false pass this phase exists to prevent.

Output: a scheme-level label token, both call sites reduced to reading it, a re-derived contrast
table, and a gate proving the colour is invariant across state.
</objective>
