# Phase 18 — UI Design Contract: Range

> Visual and interaction contract for `AeroSlider`, `AeroRangeSlider`, and `AeroProgressBar`.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker. Almost entirely pre-populated from
> `18-CONTEXT.md` (D-01..D-07), the shipped Phase 16 primitives (`AeroSurfacePrimitives.kt`,
> `AeroSurfaceStyle.kt`, `AeroOrnamentTokens.kt`), the Phase 17 button precedent this phase must
> mirror (`hoverLighten`/`flattenDisabled`/`pressedRecess`), and a direct read of the three
> current shipped component files — this phase asked the user nothing new. Every open slot below
> is Claude's-discretion territory already scoped by CONTEXT.md, resolved here to a concrete,
> implementable default, with one load-bearing architectural finding flagged explicitly (see
> Color § "Finding to confirm during planning").

## Spacing Scale

This is a three-component restyle phase, not a page layout. Two distinct concerns apply, exactly
mirroring Phase 17's framing:

### 1. Locked component geometry — VER-03, must NOT change

| Element | Locked value | Source (confirmed by direct read) |
|---------|-------------|-----------------------------------|
| `AeroRangeSlider` box height | 48.dp | `AeroRangeSlider.kt:175` |
| `AeroRangeSlider` track thickness | 4.dp | `AeroRangeSlider.kt:232` |
| `AeroRangeSlider` thumb radius / diameter | 10.dp / 20.dp | `AeroRangeSlider.kt:233` |
| `AeroRangeSlider` thumb ring stroke (pre-existing, being replaced by the new rim/bevel treatment — outer diameter must still read as 20.dp) | 2.dp | `AeroRangeSlider.kt:265` |
| `AeroProgressBar` default height (both overloads) | 8.dp | `AeroProgressBar.kt:42,83` — public default parameter, unchanged |
| `AeroProgressBar` shape | pill (`RoundedCornerShape(50)`, i.e. `cornerPx = height/2`) | `AeroProgressBar.kt:52,58,102` — unchanged; `drawAeroSurfaceCore`'s `cornerPx` must be derived the same way (Pitfall 5: never an independently-derived radius) |
| `AeroProgressBar` indeterminate segment width fraction | 0.3f (30%) | `AeroProgressBar.kt:108` — kept as the default under D-06's discretion (an existing, not invented, value) |
| Glass tooltip corner radius / padding (both sliders, unchanged look-and-feel) | 4.dp / 6.dp horiz · 2.dp vert | `AeroSlider.kt:65-66`, `AeroRangeSlider.kt:286-287` |

**`AeroSlider`'s own M3-managed track/thumb dimensions are explicitly NOT re-derived from memory.**
Material3 `SliderDefaults`' actual thumb size and track height constants for the pinned Material3
1.9.0 artifact must be read directly from the compiled/source artifact at implementation time
(same discipline as TOOL-07 and the PRIM-18 spike — verify by direct read/bytecode, never assumed
from training data) and passed through unchanged into the new custom `thumb =`/`track =` slots —
VRNG-02 forbids any size creep as a side effect of the slot swap.

| Token | Value | Source |
|-------|-------|--------|
| Bevel / rim stroke width | 1.dp | `drawAeroSurfaceCore` (PRIM-05), inherited unchanged |
| Glow-ring inner stroke | 1.5.dp | `aeroGlowRing`'s `GLOW_RING_INNER_STROKE` |

Exceptions: none newly introduced. The 2.dp/2.5.dp sub-integer stroke widths are pre-existing
primitives, listed for completeness per the Phase 17 precedent.

## Color

Framing note, same as Phase 17: these are fixed-geometry interactive controls, not a page — the
Dominant/Secondary/Accent rows are reinterpreted at the *per-state, per-region* level. All three
components resolve style from `AeroOrnamentTokens.derive(AeroTheme.colors)` (or
`colors.ornamentOverride` when set) or from `AeroTheme.colors`' own neutral tokens directly —
never new hardcoded literals.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (accent fill) | `AeroSurfaceStyle.rest(colors, cornerRadius = …)` — i.e. `ornaments.fillSplitTop`/`fillSplitBottom` (`primary.lighten(0.08f)`/`primary.darken(0.12f)`) | `AeroSlider`'s active track segment, `AeroRangeSlider`'s active (between-thumbs) segment, `AeroProgressBar`'s determinate fill and indeterminate sweeping segment (D-01, D-02, D-06) |
| Secondary (neutral thumb / inactive groove) | **New style factory, see Finding below** — neutral-glass two-tone derived from `glassHighlight`/`glassSurface`/`glassBorder`, never from `primary` | All three components' **thumb(s)** (raised, neutral) and the **inactive** portion of every track/bed (recessed groove) — the classic Win7 "blue fill, silver thumb" identity (D-01) |
| Accent (10%) | `colors.primary` (only reachable via the Dominant row's ornament-derived fields above) | Reserved for: active-fill segments and the indeterminate sweep segment ONLY — never the thumb, never the inactive groove/bed |
| Destructive | not applicable | No destructive-action variant in scope for VRNG-01..09 |

### Finding to confirm during planning — the neutral thumb/groove style does NOT yet exist as-is

`AeroSurfaceStyle.rest(base, cornerRadius)` derives `fillTop`/`fillBottom` from
`ornaments.fillSplitTop`/`fillSplitBottom`, which are **already `base.primary`-derived** (per
`AeroOrnamentTokens.derive()`, confirmed by direct read) — this is exactly what makes `rest()`
correct **as the accent fill** (mirrors the Phase 17 button finding). But D-01 requires the thumb
and inactive groove to be **neutral**, and `rest()` cannot supply that — passing it unmodified to
`aeroThumbSurface`/`aeroGroove` would render an accent-tinted thumb, contradicting D-01.

**Resolution (concrete, not hand-wavy):** add one new style-factory function in
`theme/AeroSurfaceStyle.kt` — `AeroSurfaceStyle.neutralRest(base: AeroColorScheme, cornerRadius: Dp)`
— following the exact same pattern Phase 17 added its own transforms (`pressedRecess`,
`flattenDisabled`, `hoverLighten`) in that file, not a new drawing primitive (Phase 16 already
shipped `drawAeroSurfaceCore`/`aeroThumbSurface`/`aeroGroove` — this phase only supplies a
*different style value* into those existing functions, which is "consuming the primitives layer,"
not "building a new one," per the phase boundary). Suggested field derivation, reusing only
already-neutral tokens and the already-shipped `Color.lighten()`/`darken()` helpers:

| Field | Derivation |
|-------|-----------|
| `fillTop` | `base.glassHighlight.lighten(0.12f)` |
| `fillBottom` | `base.glassSurface.darken(0.06f)` |
| `glossColor` | `ornaments.glossHighlight` (already neutral — reuse as-is) |
| `bevelLight` | `base.glassHighlight.lighten(0.20f)` |
| `bevelShadow` | `base.glassBorder.darken(0.15f)` |
| `rimColor` | `ornaments.rimLight` (already neutral — reuse as-is) |

This gives the thumb a genuine silvery/neutral-glass identity distinct from the accent fill on all
three themes, including `Classic`'s fully-opaque tokens (RGB-mix, not alpha — PRIM-01/14 safe).
Exact lighten/darken magnitudes above are Claude's discretion within the "spirit of Aero" band
(CONTEXT.md), to be spot-checked on AeroBlue/AeroDark/Classic at first implementation (PRIM-16
carries forward).

### Per-region, per-state contract

**Active accent fill** (`AeroSlider` active track / `AeroRangeSlider` between-thumbs segment /
`AeroProgressBar` determinate fill) — no hover/press state of its own; hover/press live on the
thumb, not the fill (VRNG-03/VRNG-05 scope the interactive states to thumbs):

| State | Style | Notes |
|-------|-------|-------|
| Rest (enabled) | `AeroSurfaceStyle.rest(colors, cornerRadius = trackCornerRadius)` used as-is | Gloss height fraction proportional to the thin track, per D-02 — `glossHeightFraction` may be tuned down from the shared 0.32 default toward the lower end of the ~30–35% band if the seam/bevel reads too heavy on a 4.dp track; err toward clean, not ornate (D-02 Claude's-discretion clause) |
| Disabled | `rest(colors, …).flattenDisabled(colors)` — reuses Phase 17's exact transform | Replaces the old `alpha = 0.4f` overlay everywhere (`AeroSlider`'s `SliderColors`, `AeroRangeSlider`'s `.copy(alpha = 0.4f)`) — do not keep the alpha-fade path per D-07 |

**Neutral thumb** (`AeroSlider`'s custom thumb slot / `AeroRangeSlider`'s per-thumb draw):

| State | Style | Extra cue |
|-------|-------|-----------|
| Rest | `AeroSurfaceStyle.neutralRest(colors, cornerRadius = thumbRadius)` | — |
| Hover | `neutralRest(…).hoverLighten()` (reuses Phase 17's exact fill-brighten transform, `Color.lighten` RGB-mix) | `Modifier.aeroGlowRing(active = hovered && enabled, glowColor = ornaments.hoverGlow, cornerRadius = thumbRadius)` chained BEFORE `aeroThumbSurface` (ordering rule, PRIM-06 usage contract) — verify the bloom is not clipped by the M3 thumb slot's own bounds (D-03's load-bearing check) |
| Press / drag | `neutralRest(…)` **unmodified fill** (deliberately NOT `pressedRecess` — D-04: a dragged thumb stays raised, it does not invert like a pressed button) + `.copy(glossAlpha = glossAlpha + 0.06f)` for a slightly brighter gloss as the active-drag cue | `aeroGlowRing(active = pressed \|\| isDragging, glowColor = ornaments.hoverGlow.lighten(0.15f), cornerRadius = thumbRadius)` — an intensified/brighter glow than hover's, per D-04; applied **independently per thumb** on `AeroRangeSlider` (VRNG-05) |
| Focus (no hover) | `neutralRest(…)` unmodified | `aeroGlowRing(active = focused && enabled, glowColor = colors.borderSelected, cornerRadius = thumbRadius)` — same distinct focus-vs-hover token split as Phase 17's D-04, so hover-only/focus-only/co-active remain distinguishable |
| Disabled | `neutralRest(colors, …).flattenDisabled(colors)` | No glow ring active regardless of interaction source state |

**Inactive neutral groove** (`AeroSlider` inactive-track / `AeroRangeSlider` full-width base track /
`AeroProgressBar` recessed bed under both determinate and indeterminate fills):

| State | Style |
|-------|-------|
| Rest (enabled) | `aeroGroove(neutralRest(colors, cornerRadius = …))` / `drawAeroGroove(neutralRest(…), cornerPx)` for the Canvas path — the groove function's own fill/bevel swap + inner-shadow cue apply automatically, no bespoke recess code |
| Disabled | `aeroGroove(neutralRest(colors, …).flattenDisabled(colors))` — same transform applied before the groove swap, for consistency with the thumb/fill disabled treatment |

**Indeterminate sweep segment** (`AeroProgressBar`, D-06): a single accent-glass segment using the
same `rest(colors, cornerRadius = height/2)` fill/gloss/bevel core as the determinate fill, drawn
at the current 30%-of-width fraction (unchanged from shipped), with its leading and trailing edges
additionally faded via a horizontal alpha mask so the segment's own edge colors reach
`baseColor.copy(alpha = 0f)` (PRIM-14 — never `Color.Transparent`) rather than a hard-edged
rectangle. Exact falloff width/shape is Claude's discretion (CONTEXT.md), reviewed on all three
themes. Timing stays the shipped 1500ms `LinearEasing` restart, `RepeatMode.Restart` — **no
ping-pong** (VRNG-08; `RepeatMode.Reverse` is explicitly banned).

**Optional running sheen** (`AeroProgressBar`, D-05, VRNG-07): a *separate* traveling highlight
layered on top of the (always-on) static determinate gloss, gated by a new optional parameter
defaulting to `false`. When enabled, sweeps left→right similar in spirit to the indeterminate
segment's motion but as a highlight overlay, not a replacement fill — exact easing/duration is
Claude's discretion, reviewed on the three-theme pass; the static gloss must remain visible with
the sheen off (D-05's exact boundary).

### Pattern 3 reuse (VRNG-09)

Anywhere an animated visual transition and a live drag write the same on-screen property — e.g. a
thumb's glow/gloss brightness bump transitioning in on hover-enter, but the user is actively
dragging that same thumb — the locked `AeroPanelGroup` Pattern 3 applies: the animated value reads
a target-only state (`animateFloatAsState` or equivalent) during idle transitions, but while
`isDragging`/`pressed` is true for that thumb, the value is **written directly** (no animation
lag), matching Pattern 3's "animation reads target, drag writes directly, `isDragging` switches to
`snap()`" shape. Apply this per-thumb on `AeroRangeSlider` (each thumb's own drag state gates its
own visual snap, independent of the other thumb).

## UI Considerations

Probe classified three interactive-control surfaces: **E1** `AeroSlider` (M3-hosted, custom
thumb/track slots), **E2** `AeroRangeSlider` (Canvas, two independent thumbs), **E3**
`AeroProgressBar` (determinate + indeterminate). 8 categories probed. **3 covered, 1 backstop, 4
dismissed, 0 unresolved.**

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| loading | E3 indeterminate `AeroProgressBar` | ✅ covered | Indeterminate mode IS the canonical loading-state representation for this component family (VRNG-08) — restyled to the D-06 single accent-glass sweeping segment over the recessed bed, 1500ms restart, no ping-pong. Determinate mode (VRNG-06) is the "known-quantity progress" counterpart, both covered by the Color § per-state contract above |
| populated | E1, E2, E3 | ✅ covered | Every value along each control's continuous range renders identically through the same style resolution (rest/hover/press/focus/disabled) — there is no separate "has data" vs "no data" branch for a bounded numeric control; 0%/min-value and 100%/max-value are ordinary points on the same scale, not a special empty case |
| partial | E2 `AeroRangeSlider` | ✅ covered | The active (accent-filled) segment between the two thumbs IS the "partial selection of the full range" state — pre-existing behavior (`AeroRangeSlider.kt`'s active-track draw), unchanged logic, now rendered with the accent glass fill (D-01) instead of a flat `colors.primary` line |
| overflow | E1, E2 drag tooltip | 🧪 backstop | **Statement:** the drag-value tooltip pill is restyled to match the new glass treatment but its position logic is untouched this phase (`AeroSlider`'s tooltip stays fixed top-center per its own pre-existing TODO comment — "track tooltip x to thumb position" is not this phase's scope; `AeroRangeSlider`'s tooltip DOES track thumb x via `offset(x = thumbXDp - 16.dp)`, which can already overflow the container near either edge — a pre-existing condition, not newly introduced). **Verification (backstop):** confirmed at the three-theme visual review that the restyle introduces no NEW overflow beyond what already existed pre-migration |
| empty | E1, E2, E3 | dismissed | No data-collection empty-state concept applies to a bounded numeric control — confirmed against the Copywriting Contract's empty-state rows (marked not applicable) |
| error | E1, E2, E3 | dismissed | No error/failure rendering in scope; `enabled = false` is the only negative state (Copywriting Contract, Color § Disabled) |
| zero-one-many | E1, E2, E3 | dismissed | No collection/list semantics on any of the three components |
| long-text | E1, E2 tooltip; E3 percent label | dismissed | All copy is fixed-format bounded numeric text (`"%.2f"` value, `"NN%"` integer percent) — no wrap/truncation handling required, unchanged from shipped |
