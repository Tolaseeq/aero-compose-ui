> verified by gsd-ui-checker. Almost entirely pre-populated from `20-CONTEXT.md` (D-01..D-16),
> `20-DISCUSSION-LOG.md`, and direct reads of the shipped Phase 16–19 code

> this phase asked the user nothing new on the visual axis.

> **Desktop** component library, not React/Next.js/Vite. No `components.json` exists; the shadcn
> gate is not applicable and is not prompted (confirmed again this phase — no new frontend
> tooling introduced).
>
> **Scope note — what this UI-SPEC covers vs. what it doesn't.** Phase 20 is a verification phase:
> no component is restyled (20-CONTEXT.md "Phase Boundary"). This contract governs the ONE new
> visual surface this phase adds (the permanent cross-component review section, SHW-15/D-04), the
> ONE visual change this phase makes to existing components (the folded `AeroButton` /
> `AeroSegmentedControl` label-contrast fix, D-12/D-13), and the state-completeness top-ups to the
> four existing sections. It does **not** re-derive the mechanics of VER-01/02/03/04/05/06 (grep
> gates, snapshot test, keyboard test, scratch consumer) — those are gate/test engineering, fully
> specified in `20-CONTEXT.md` D-05..D-11, D-14..D-16, and are the planner's/executor's direct
> input from that file, not a design-contract concern. Where a gate has a user-visible surface

### The folded contrast fix (D-12/D-13) — the one color-mechanism change this phase makes

**Constraint (verbatim from the user, `20-DISCUSSION-LOG.md`):** *"Нельзя просто так взять и
изменить бекграунд. Он должен быть ЕДИНЫМ для подобных элементов… ЕДИНЫЙ СТИЛЬ."* — one shared
mechanism for `AeroButton`'s and `AeroSegmentedControl`'s fill/label, never two independently
retuned constants (this is exactly why gap G5 was rejected at 19-12).

**Root cause (confirmed by direct read of `AeroButtonSurface.kt:116-123`):** the `Text` sets no
`color =`; the label resolves to ambient `LocalContentColor` (`onBackground`), which is
byte-identical to `onSurface` in all three schemes — it has never actually been chosen for
contrast against the button's own fill.

**Contract — mechanism, not a per-component constant:**

1. A **single function** (owned by `AeroButtonSurface.kt`, imported by `AeroSegmentedControl.kt`
   exactly like `FILLED_FILL_TOP_DARKEN`/`PRESSED_INNER_SHADOW` already are — same cross-package
   pattern, no new import style) resolves the label color **algorithmically from the resolved
   fill**, not from a hardcoded per-theme literal. It picks between two fixed candidates — a
   near-black and a near-white token — by computed WCAG relative-luminance contrast against the
   **worse** (lower-contrast) of `fillTop`/`fillBottom`, and both `AeroButtonSurface`'s `Text` and
   `AeroSegmentedControl`'s segment `Text` call it identically. This is the "one source of truth"
   D-12 requires: a color a component asks a shared function for, not a color a component author
   picks by eye.
2. **Starting values, derived this phase from the shipped fill constants** (`FILLED_FILL_TOP_DARKEN
   = 0.20f`, `FILLED_FILL_BOTTOM_DARKEN = 0.36f`, applied to each theme's `primary` — computed by
   direct WCAG relative-luminance formula against `Color.Black`/`Color.White` candidates):

   | Theme | fillTop contrast (label = black) | fillBottom contrast (label = black) | fillTop (label = white) | fillBottom (label = white) | Wins |
   |-------|-----------------------------------|----------------------------------------|----------------------------|--------------------------------|------|
   | AeroBlue | 6.78 | 4.56 | 3.10 | 1.97 | **black** — clears 4.5:1 on both stops, though fillBottom's 4.56 margin is thin |
   | AeroDark | 7.71 | 5.10 | 2.65 | 1.42 | **black** — clears comfortably on both stops |
   | Classic | 3.99 | 2.88 | 5.26 | 7.30 | **white** — black fails fillTop; white clears both stops |

   These confirm the mechanism is genuinely per-theme by construction (light pastel primaries in
   AeroBlue/AeroDark want a dark label; Classic's mid-saturation blue wants a light label) — this
   is expected variation across themes' own palettes, not per-component drift, and is exactly the
   kind of "themes are inherently different" case the standing G4 deferral already acknowledges
   for ornament brightness.
3. **AeroBlue's fillBottom margin (4.56, only 0.06 above the 4.5 floor) is flagged as tight.** If
   the value-level contrast test (D-13) measures below 4.5 once implemented against the library's
   actual `Color.darken()` RGB-mix math (this phase's estimate uses the same formula but should be
   confirmed programmatically, not trusted by hand), the fix is to widen `FILLED_FILL_BOTTOM_DARKEN`
   very slightly for that theme — **not** to special-case the label color per theme beyond the
   black/white pick already specified, and **not** to retune `AeroSegmentedControl` separately
   (D-12 still applies to any such follow-up).
4. **The mechanism must be verified against BOTH fill stops in ALL THREE themes** (WCAG 4.5:1
   normal-text floor, per the folded todo) — this is the acceptance bar the three-theme sign-off
   checks visually and D-13's test checks at the value level.
5. **Not garish** (user's constraint): a hard-black or hard-white label on a colorful gradient fill
   reads as a standard flat/native OS button label (Win7 Aero buttons do use dark labels on light
   chrome and vice versa) — this is the expected, intended look, not a compromise.

**Both stops, all three themes, one mechanism** — this is the literal acceptance bar; it is not
satisfied by fixing only the theme(s) that were furthest below the floor.

## UI Considerations

> Populated by the ui-phase UI-consideration probe (post-verification). This phase's only new
> user-facing surface is the permanent **Verification** review section (SHW-15/D-04); the four
> existing sections are audited for state completeness only (no restructuring), and the scratch
> consumer is a separate, minimal window (VER-05) outside the showcase's own conventions. Element
> classification: **E1** the Verification section's eight-component grid = `list-collection`,
> **E2** each individual demo control inside it = `interactive-control` (identical classification
> to every prior phase's per-component demo — these are the SAME shipped components, not new
> ones), **E3** the per-component caption row = `static-content`, **E4** the scratch-consumer
> window = `interactive-control` (renders all eight, no new interaction beyond what each
> component already has).

**Focal point (Dimension 2):** each component's own rendered surface is the primary anchor inside
its demo block — unchanged from every prior phase's precedent (16/17/18/19), since no component's
own visual weighting changes here. Across the section, all eight demo blocks read as a **uniform
grid of equals** (D-04's stated purpose: "do all eight read as one material family" is a
side-by-side comparison question — no single component may be given more visual weight than
another, e.g. via a larger card or a highlighted border, or the coherence judgment itself would be
biased by the layout).

### 🧪 Backstop (6)

Each lifts into `must_haves.truths`. At verify time a backstop is confirmed only by explicit
evidence or routes to `insufficient_spec → human_needed` — never a silent pass.

**E1 · overflow** — `verification: backstop`
- **statement:** Eight demo blocks in one section is the largest single-section grid the showcase has hosted (larger than `PrimitivesSection`'s six primitive groups, Phase 16). The section must render inside the showcase's existing outer `verticalScroll` container (`ShowcaseApp.kt:66-70`) without introducing a second, nested scroll region — nested scroll containers are a documented showcase anti-pattern this project avoids elsewhere.
- **backstop:** Confirmed at the three-theme sign-off (coherence pass) — the section scrolls as part of the single outer `Column`, not independently.

**E1 · long-text** — `verification: backstop`
- **statement:** Two of the eight components carry the pre-existing, documented overflow risk from Phase 19's own UI-SPEC (`AeroSegmentedControl`'s and `AeroListItem`'s long-label backstops, both PRE-EXISTING and explicitly out of VSEL/VLST scope). Placing all eight side-by-side in one dense grid is a NEW context for that pre-existing risk — a long label in the coherence grid could visually distort the grid's uniform-weight framing (Focal point note above) more noticeably than it did in `SelectionSection`/`ListSection`'s own spaced-out demo rows.
- **backstop:** At the three-theme sign-off, confirm the coherence grid's realistic (short, representative) captions/labels do not trigger this pre-existing overflow; if the reviewer deliberately exercises a long label to test it, confirm the grid's layout absorbs one widened block without breaking the row/grid alignment of its neighbors (each block's own bounds, not a shared fixed-width column, per the Focal-point equal-weight note).

**E2 · overflow / long-text** (combined, single risk per the established de-dup rule) — `verification: backstop`
- **statement:** Identical to the risk already recorded in the Phase 17/19 UI-SPECs for `AeroSegmentedControl`/`AeroButton` label truncation and `AeroListItem` text overflow against its clipped pill — nothing new is introduced by this phase's controls themselves. The NEW factor is the contrast fix (D-12): a black-on-light or white-on-dark label, once resolved algorithmically, must remain legible at every label length the existing backstops already cover, not just the short demo strings.
- **backstop:** Re-confirmed as part of THIS phase's three-theme sign-off (D-01's hybrid scope explicitly covers `AeroButton`/`AeroOutlinedButton` state-by-state because they changed) — the reviewer checks the contrast-fixed label against a long/truncating label, not only the default short one.

**E4 · overflow** — `verification: backstop`
- **statement:** The scratch consumer (VER-05) is deliberately written outside the showcase's own layout conventions (D-15) — it has no inherited scroll/padding contract to rely on. All eight components must render inside its window without clipping, at whatever minimal layout the scratch consumer author chooses.
- **backstop:** Confirmed when the scratch consumer is run and visually inspected (D-15's "launches and renders" bar) — not assumed from the showcase's own layout correctness.

**E4 · zero-one-many** — `verification: backstop`
- **statement:** The scratch consumer must render exactly the milestone's eight named components (same fixed list as E1/E3), proving the published artifact's public API surface is reachable by a stranger — not a subset chosen for convenience.
- **backstop:** Confirmed by the same run as the row directly above (D-15) — checked against the milestone's own eight-component list, not left to the scratch consumer author's discretion on which subset "counts."
