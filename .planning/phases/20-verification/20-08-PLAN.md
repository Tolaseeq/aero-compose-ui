<objective>
Convert the mechanically-checkable half of the SHW-16 sign-off checklist into permanent, re-executed
Compose UI-test gates, so the human pass in 20-07 is reduced to what only a human can answer.

**Why this exists.** The 20-07 checklist asks a human to verify, by eye and by hand, a per-state
matrix across three themes, a ~150ms label transition, a focus-ring wiring rule, and 1dp contour
rounding at fractional DPI. Every one of those is deterministic and measurable. Driving them by hand
produces a one-time transcript in a protocol file that never re-executes — which is precisely the
practice this milestone already rejected: D-08/VER-06 exist because Phase 17's one-time transcript
was found insufficient and replaced with in-file proof that re-runs on every build.

The infrastructure is already present and already used in this codebase — `compose.uiTest` is on the
test classpath; `captureToImage()`, `performMouseInput`, `performKeyInput`/`requestFocus`, and
`CompositionLocalProvider(LocalDensity provides Density(...))` each already appear in shipped tests.
Only `mainClock`/`autoAdvance` is new.

**What this plan deliberately does NOT attempt** is as important as what it does. Cross-component
aesthetic coherence, the legibility judgment on AeroDark's authorized 4.079 contrast exception, and
real OS-compositor DPI behaviour are not machine-checkable. They stay with 20-07. This plan shrinks
the human checklist; it does not replace it, and any claim that it closes SHW-16 on its own would be
exactly the false pass this phase exists to prevent.

Output: four new test gates under `library/src/test/kotlin/`, no production change.
</objective>

  <files>library/src/test/kotlin/com/mordred/aero/verification/VER08SegmentLabelFlipTest.kt</files>
  <read_first>
    - library/src/main/kotlin/com/mordred/aero/components/buttons/AeroButtonSurface.kt — resolveLabelColor, which derives the label from the CURRENT fill.

  </read_first>
  <action>
Because `resolveLabelColor` derives the label colour from the animating fill, the label must flip
when the fill crosses the contrast midpoint. That flip is real and expected; an OSCILLATING flip is
the defect, and at ~150ms the eye cannot tell the two apart.

Set `mainClock.autoAdvance = false`, click a segment, and step the clock frame by frame to the end
of the selection animation, sampling the resolved label colour at each step. Assert the colour
changes AT MOST ONCE across the whole sequence, in all three schemes. Assert the sampled frame count
is non-zero so a clock that never advanced cannot pass vacuously.

Include the D-08 proof: a synthetic colour sequence that oscillates must be rejected by the same
comparison, and a monotone one accepted.
  </action>
  <verify>`./gradlew :library:test --tests "*VER08*"` exits 0; the oscillating fixture is proven red.</verify>
