<planner_finding>
**The mechanism deviates from the literal wording of G2's `fix_direction`, and here is why.**

19-UAT.md's G2 `fix_direction` proposes gating on `LocalInputModeManager.current.inputMode == InputMode.Keyboard`. That is the correct *intent* (focus-visible semantics) but the named mechanism cannot be relied on here, and the mechanism was a diagnosing agent's suggestion, not a locked user decision (19-CONTEXT.md has no D-XX on focus-visible).

Evidence gathered during planning, by inspecting the resolved Compose Multiplatform 1.11.1 desktop artifacts in the Gradle cache:
- In `ui-desktop-1.11.1.jar`, the only non-manager class that calls `requestInputMode` is `androidx.compose.ui.node.RootNodeOwner`, and it references both `InputMode.Touch` and `InputMode.Keyboard`. Which pointer types map to which mode is not determinable from the bytecode.
- In `foundation-desktop-1.11.1.jar`, JetBrains ships `InputModeFilterIndication` / `InputModeFilterInteractionSource`, which wraps an `InteractionSource` and filters `FocusInteraction.Focus` / `FocusInteraction.Unfocus` on an `isKeyboardMode` check. So the platform does use the input-mode gate for focus indication on desktop — but it applies it to the platform `Indication`, which this library deliberately disables (`indication = null` on every interactive component, P-01).

Net: if a desktop mouse press requests `InputMode.Touch`, the input-mode gate works; if it requests `InputMode.Keyboard` (which is how Compose classifies "non-touch input" in general), the gate is a silent no-op and the reported defect survives the fix. An interaction-derived gate is correct under BOTH behaviours, needs no platform assumption, and is unit-testable without a Compose runtime.

The observable contract G2 asks for is unchanged and is what the `must_haves.truths` above assert: mouse click → no focus cue; Tab → focus cue; hover cue untouched; element still focusable and keyboard-operable. Record this deviation in the SUMMARY.
</planner_finding>
