<objective>
Close the two wiring warnings that sit in the same failure class as CR-02: per-segment state memoised by slot position rather than by option identity (WR-03), and a redundant second hover emitter on every one of the three restyled components (WR-04).

Purpose: WR-04's duplicate emitter puts two hover-enter and two hover-exit events on one interaction source for every pointer transit. The shared collector survives that because it is reference-counted; the focus-visibility reducer does not, because it models hover as a plain boolean — so the first exit clears it while a second enter is still outstanding. Today the emissions happen to arrive batched and the press lands inside the true-window, but the model is wrong in exactly the way that produced CR-02, and CR-02's fix now makes the reducer's hover field survive longer, which widens rather than narrows the window in which a desync matters. WR-03 is the same shape one layer up: state that belongs to an option is keyed to a slot, so changing the option list transfers one segment's interaction and animation state to another.
Output: segment composition keyed to identity, exactly one hover emitter per interaction source, source guards rewritten to state that contract, and a behavioural test proving hover still works rather than trusting a decompiled artifact.
</objective>

<scope_fence>

- **WR-07 is deferred.** Duplicate options, an absent `selected`, and an empty option list all remain unguarded. That is why Task 1 keys on index-and-value rather than on value alone: value-only keys would collide under duplicates, which the component does not prevent.

<planner_finding>
**Why removing the emitter, and not counting the enters, is the route taken.**

WR-04 offers two fixes: remove the duplicate emitter, or change the reducer's hover field into a counter so duplicate emissions cannot desync it. The developer scoped this round to the first. That is also the better fix on its own merits: a counter would make the reducer tolerate a wiring mistake rather than remove it, and it changes the shape of a data class that plan 19-09 has just fixed and proven — two edits to one type in one round, the second of which weakens the first's test's meaning. The counter remains available as a follow-up if a future component genuinely needs two emitters.

**Why the three components need three different treatments, not one.**

They look identical at the call site and are not:

| Component | Interaction modifier on that source | Applied when | Correct treatment |
|---|---|---|---|
| `AeroSwitch` | toggle modifier, given the same source | always (WR-06 deferred) | remove the explicit emitter outright — the toggle modifier is always there to emit |
| `AeroSegmentedControl`, per segment | selection modifier, given the segment's own source | always | remove the explicit per-segment emitter |
| `AeroSegmentedControl`, outer strip | **none** — the control-level source has no interaction modifier at all | n/a | **keep** its explicit emitter; it is not a duplicate |
| `AeroListItem` | click modifier, given the same source | **only when a click handler was supplied** | make the explicit emitter the else-branch of that same condition |

The list row is the one that would break under a naive removal: a display-only row has no interaction modifier at all, so its explicit emitter is that path's only hover source. Folding it into the else-branch of the existing condition yields exactly one emitter on both paths and, as a bonus, lets it carry the enabled flag.

**Why VLST-04 still holds after the switch loses its literal token.**

VLST-04 requires that components newly gaining hover copy the list row's existing interaction-source-plus-collector pairing rather than inventing pointer-position tracking. After this plan: every component still resolves hover from `rememberAeroInteractionState(source)`, which reads the shared collector; every component still routes hover through a `MutableInteractionSource`; and the negative guards banning raw pointer input remain in all three source suites. What changes on the switch is only WHICH modifier feeds that source — its toggle modifier instead of a second explicit one. The literal token also survives in two of the three files (the list row's display-only branch and the segmented control's outer strip), so the pattern remains present and readable in the codebase.

The switch's existing guard message asserts that its toggle modifier "does not report hover for free". WR-04 refuted that against the resolved artifact. Rather than trust either the old message or the review's decompilation, Task 2 turns the premise into a test that runs on the same Compose version the library actually builds against. If that test goes red, the premise is false, the removal is wrong, and the executor must stop and report rather than proceed — see Task 3's fallback clause.
</planner_finding>
